fetch(..., {credentials:'include'}) resolves only when the response carries access-control-allow-credentials: true and a non-wildcard allow-origin, so the two 200s are the browser-side proof.
Console between [log] A6-MARK-START and [log] A6-MARK-END: 0 entries (0 CORS errors).
Probe note: an earlier exploratory call fetched /check/cors with credentials:'include' and was blocked ("must not be the wildcard '*' when the request's credentials mode is 'include'"). That was the probe's own mistake, not the app: /check/cors answers allow-origin * by design, and @sanity/client calls it with credentials only when the client uses withCredentials. The web client uses a browser token (Authorization header), so it calls /check/cors without credentials, as re-probed above (200, allowed true).
